1. 先看懂整体结构

AICoding 不是“让 AI 随便写代码”，而是把 AI 放进一套可控流程里：先定规则，再给工具，再指定方法，最后用验证收尾。 这也是为什么单靠“一个聪明模型”不够，真正稳定的是整条链路。

组成 你可以把它理解成 它主要解决什么 一句话例子
系统提示词 规矩 限制 AI 不能乱猜、不能跳步骤、不能一次做太大 “不确定就查证，不能编”
Skill 做事方法 把复杂任务拆成可重复的工作流 “先规划，再实现，再验证”
MCP 外接工具 让 AI 去查资料、读文档、看代码、拿上下文 EXA / Context7 / CodeGraph
模型 大脑 决定推理能力、速度、成本、稳定性 GPT-5.5 / GPT-5.3-Codex
给小白的记忆法：系统提示词管“不能怎么做”，Skill 管“应该怎么做”，MCP 管“去哪儿查”，模型管“能做多好”。

2. 核心系统提示词

这部分是整份教程最重要的地方。你给 AI 的“系统提示词”不是普通需求描述，而是长期有效的行为底线。 它的作用不是让 AI 更会说话，而是让 AI 更少幻觉、更少乱改、更少一次性做太大。

推荐理解方式

系统提示词是“全局规矩”。它应该稳定、简短、可重复，不要把这次任务的细节塞进去。

它能降低什么风险

减少空想、减少编造接口、减少大改动失控、减少一次性写太多、减少“看起来像对”的假答案。

重点：系统提示词不能“保证” AI 绝对不幻觉，但它可以把幻觉的机会压低，把错误更早暴露出来。 
在编码过程中以下要求必须遵守，禁止跳过或忽略任何一步：
第一、禁止空想和捏造代码，如果遇到不确定的代码，可以使用 EXA、Context7、网络搜索 等功能来获取足够确定的代码。
第二、编写过程中必须考虑代码拆分及规划，严禁单文件超过 1000 行代码。（文档文件可忽略该限制，但是代码文件必须严格遵守！）
第三、单次提交/编写代码不要太多（最好不要超过 1000 行），分少量行数多次提交。
第四、你可以自己评估需求复杂度，自行决定是否使用子 Agent（subagents）并行来高效且完整地完成需求，具体数量由你自己来定。
第五、【可选】需要编写文档时，在没有强制要求的情况下，默认使用单文件 HTML 格式编写文档。

第 1 条：不准空想

这是防幻觉的第一层。AI 不知道时，必须去查 EXA、Context7、CodeGraph 或网络，而不是硬猜一个“看起来合理”的答案。

第 2 条：先拆分再动手

把复杂任务拆成小块，能让 AI 更容易保持上下文，也更容易发现哪里理解错了。单文件过大，很容易让错误滚雪球。

可选建议

第 5 条：文档默认 HTML（可选）

这一条不是必须项，而是交付习惯。HTML 方便开发人员直接打开查看、做样式和交互，也便于后续继续修改；代价是比 Markdown 更消耗 token，通常大约是 3-4 倍。

第 3 条：少量多次

一次改太多，出问题时很难定位。少量多次的价值不是慢，而是让每一步都能验证、都能回滚。

第 4 条：复杂度高就用子 Agent

有些任务可以并行切开，比如多个独立问题、多个模块、多个测试文件。让子 Agent 各做一块，比一个 AI 硬扛更稳。

3. 提示词怎么写

好提示词不是“更长”，而是“更可执行”。当前官方建议的方向也很明确：先说目标，再写约束，再说输出格式，再说明遇到缺信息时怎么办。

一个好提示词的公式

  • 目标：你到底想完成什么。
  • 背景：项目是什么、现在卡在哪里。
  • 约束：技术栈、不能做什么、代码量限制。
  • 工具：允许用哪些工具查证据。
  • 验证：完成后如何确认对不对。
  • 输出：你要它以什么格式回答。

新手最容易犯的错

  • 只说“帮我写一下”，没有目标。
  • 不给背景，让 AI 盲写。
  • 一次塞太多要求，自己都看不清。
  • 不让查资料，却要求答案绝对准确。
目标：
请完成什么事情。

背景：
项目是什么，当前状态是什么，哪里不懂。

约束：
1. 不要空想，遇到不确定先查证。
2. 代码要拆分，不要一次改太多。
3. 需要时使用 EXA / Context7 / CodeGraph。
4. 如果信息不足，先问我最关键的问题。

输出：
先给方案，再分步骤执行，最后给验证结果和风险说明。

写代码时的提示词

重点是让 AI 先理解目标和边界，而不是直接开写。

你现在先不要直接写代码。
请先做三件事：
1. 读懂我给你的需求和现有约束
2. 不确定的地方先查资料，不要猜
3. 给我一个分步实施方案，说明每一步怎么验证

我更关心：正确、可维护、可验证，而不是一次写很多。

查资料时的提示词

关键是把“查什么”和“为什么查”说清楚。

请使用 EXA / Context7 / 官方资料查证下面的问题：
1. 最新版本是什么
2. 正确用法是什么
3. 有没有我应该避免的坑

请把结论和来源分开写，不要只给一个猜测答案。

排查问题时的提示词

先找根因，再修。不要上来就乱改。

请先定位根因，不要直接给修复方案。
请按这个顺序处理：
1. 复述我遇到的问题
2. 判断最可能的根因
3. 告诉我应该先检查哪里
4. 再给最小修复方案
5. 最后给验证方式

写文档时的提示词

把受众、结构、语气、输出格式一次说清楚。

请写一份面向小白和进阶用户都能看懂的教程文档。
要求：
1. 先讲概念，再讲方法，再讲例子
2. 语气清楚、直接、不要空话
3. 有表格、有模板、有操作步骤
4. 如果有不确定的事实，先查证再写
5. 输出为单文件 HTML

4. MCP 是什么

MCP 的作用很简单：给模型一套标准接口，让它可以调用工具、读取资源、使用预设提示词。 你可以把它理解成“AI 的外接标准插口”，而不是模型本身。

Tools

让 AI 做事，比如搜索、读取、分析、调用接口、执行特定动作。

Resources

让 AI 读取上下文，比如文件、数据库结构、项目资料、特定文档。

Prompts

让服务器提供可复用的提示模板，用户可以显式选择使用。

一句话：MCP 不是模型，也不是 Skill。它是模型和外部工具、数据之间的标准桥梁。

4.1 三个最常见的 MCP 工具

EXA

适合：查最新公开资料、网页、文章、公告、搜索结果、代码示例。

  • 适合“现在最新是什么”这种问题。
  • 适合查官方文档以外的公开网页资料。
  • 适合让 AI 先检索，再总结。

Context7

适合：查库、框架、SDK 的最新官方文档和代码示例。

  • 适合“这个库现在正确写法是什么”。
  • 适合按版本查，减少旧 API 幻觉。
  • 适合写代码前先补文档上下文。

CodeGraph

适合：理解项目代码结构、符号关系、调用链、影响范围。

  • 适合先看代码地图，再决定怎么改。
  • 适合追踪“谁调用了谁”。
  • 适合大项目和多人项目。

什么时候用 EXA

当你需要的是“外部世界”的最新信息，比如最新公告、教程、文章、案例、别人的做法，就优先 EXA。

请用 EXA 查一下这个问题的最新公开资料：
主题：OpenAI 的 GPT-5.5 最新官方说明
要求：
1. 只引用可靠来源
2. 先给结论，再给来源
3. 不要把旧版本信息当成现在仍然有效

什么时候用 Context7

当你要写某个库、框架、SDK 的代码，且版本很重要时，先用 Context7 查当前文档。

请用 Context7 查这个库的最新官方文档：
库名：Next.js
问题：如何在当前版本中配置 middleware 和身份验证
要求：
1. 给出正确的 API
2. 给出最小可用示例
3. 标明可能踩坑的地方

什么时候用 CodeGraph

当你要改现有代码、怕改错、怕影响别处时，先让它把项目结构和调用关系找出来。

请用 CodeGraph 先帮我理解这个项目：
1. 找出和登录相关的核心入口
2. 说明这些函数之间的调用关系
3. 告诉我这次改动可能影响哪些模块
4. 不要直接改代码，先给我代码地图

最实用的判断口诀

  • 查最新公开信息：EXA
  • 查官方库文档：Context7
  • 查项目代码关系：CodeGraph

5. Superpowers Skills 详细说明

Skill 可以理解成“可重复使用的工作方法”。它不是一次性的任务描述，而是一套稳定的做事流程。 下面这些 Skill 按照最接近真实工作流的顺序来讲。建议你先看最常用的，再看更专门的。

先看这几个最常用

  • using-superpowers：先判断该用哪个 Skill。
  • brainstorming：需求不清时先设计。
  • writing-plans：把大任务拆成可执行步骤。
  • test-driven-development：先写测试再写实现。
  • verification-before-completion：完成前先验证。

中后段常用

  • systematic-debugging：先找根因，再修复。
  • requesting-code-review / receiving-code-review：让 review 真正有用。
  • finishing-a-development-branch：收尾、合并、清理。
  • using-git-worktrees：隔离工作区。
using-superpowers 先判断当前问题应该用哪一个 Skill，而不是直接开做。
入口 Skill

作用：这是整个技能体系的入口。它提醒 AI 在开工前先判断：当前任务有没有更合适的 Skill，应该先看哪条工作流。

适合什么时候用：每次开始新对话、新任务、新动作时，尤其是你不确定该用规划、调试、验证还是 review 的时候。

核心原则：先选方法，再做事。不要“想到什么就做什么”。

给小白的理解：它像一个总开关，告诉 AI 先看说明书，再开始干活。

先检查当前任务应该使用哪个技能。
如果任务需要规划、调试、验证、review 或多步执行，请先调用对应 skill 的工作流，再继续。
brainstorming 需求还不清楚时，用来把目标、边界、方案先想明白。
先设计

作用：把模糊需求变成明确设计。先了解背景，再问关键问题，再提出 2-3 个方案，最后写成设计说明。

适合什么时候用：需求模糊、范围大、会影响很多模块、或者你本来就不确定该怎么做的时候。

核心原则：不要急着写代码。先把问题定义清楚，后面才不会返工。

给小白的理解：像做作业前先把题目读懂，确认老师到底要什么。

  • 先看项目上下文和已有约束。
  • 一次只问一个关键问题。
  • 提出 2-3 个方案并比较利弊。
先不要写代码。
请先帮我把这个需求拆清楚：
1. 它真正要解决什么问题
2. 有哪些边界条件
3. 有哪 2-3 种可选方案
4. 你推荐哪一种，为什么
5. 如果信息不够，请先问我最关键的一个问题
writing-plans 把需求写成真正能执行的计划，细到文件、步骤、测试和提交。
写计划

作用：把一个大任务拆成很多很小的动作，每一步都知道要改哪个文件、先写什么测试、如何验证、什么时候提交。

适合什么时候用：你已经知道要做什么，但任务太大，不适合直接开工的时候。

核心原则：计划要能被另一个完全不熟悉项目的人照着做。不能有“适当处理”“补一下”“类似地实现”这种空话。

给小白的理解：它像把“我要做一个项目”写成“今天先做第 1 步，明天做第 2 步”。

  • 明确要改哪些文件。
  • 每一步都给出可运行的验证方法。
  • 不要留下 TBD、TODO 和模糊说法。
请为这个需求写一份可执行计划。
要求：
1. 列出要创建或修改的文件
2. 每个任务都拆成 2-5 分钟的小步骤
3. 每一步都写清楚要跑什么验证命令
4. 不允许使用 TBD / TODO / 模糊表述
5. 如果任务太大，请先拆成多个独立子任务
using-git-worktrees 给当前工作单独开一个隔离工作区，避免互相污染。
隔离工作区

作用：在一个独立的 git worktree 里做开发，避免你当前主工作区被打乱，也便于并行做多个任务。

适合什么时候用：开始中大型改动之前，或者你准备按计划执行一整套任务时。

核心原则：先确认工作区目录、安全性、基础依赖和 baseline 测试，再开始改。

给小白的理解：像给这次任务单独开一张桌子，不把别的东西混进来。

test-driven-development 先写失败测试，再写最小实现，最后重构。
先测后写

作用：用测试先定义行为，再写代码满足它。这样能避免“代码看起来对，但其实不对”。

适合什么时候用：任何新功能、bug 修复、重构和行为修改。

核心原则：你必须先看到测试失败，才能证明它真的在检查你想要的行为。

给小白的理解：先写题目再写答案，避免你把答案当成标准。

  • 写一个明确、单一的测试。
  • 先跑它，确认它真的失败。
  • 再写最小代码让它通过。
systematic-debugging 先找根因，再提出单一假设，再验证，再修复。
先找根因

作用：当程序出错时，不靠猜。先看错误信息，再复现，再找最近变化，再定位根因，最后做最小修复。

适合什么时候用：任何 bug、测试失败、构建失败、行为异常、性能问题。

核心原则：症状不等于原因。修症状很快，修根因才稳定。

给小白的理解：肚子疼先找原因，不是先乱吃药。

  • 先确认现象是稳定可复现的。
  • 每次只验证一个假设。
  • 连续尝试多次还不行，就要怀疑架构或设计。
verification-before-completion 在说“做完了”之前，先拿出新的验证证据。
先验证

作用：防止“我觉得差不多了”这种假完成。只有跑过验证、看过结果，才能说完成。

适合什么时候用：任何准备收尾、提交、发 PR、继续下一步的时候。

核心原则：没有新验证，就不能新结论。

给小白的理解：不是“看起来好了”就算好，而是要有检查结果。

requesting-code-review 在关键节点主动发起 review，而不是等出大问题。
请求 review

作用：让另一个审查视角来查问题，尤其是大功能完成后、提交前、重构前。

适合什么时候用：完成任务、实现重要功能、合并前。

核心原则：早 review，比晚补救便宜得多。

给小白的理解：请别人帮你挑错，不要等错误进仓库才发现。

receiving-code-review 收到 review 后，先核实，再判断，再改，不做表面认同。
接收 review

作用：面对 code review 意见时，先看是否真的对当前项目成立，再决定改不改，不盲从，也不嘴上客气。

适合什么时候用：收到外部或内部 review 建议时。

核心原则：技术正确性优先。先验证，再响应，再实现。

给小白的理解：别人提意见，不代表一定对；要先确认再改。

dispatching-parallel-agents 多个互不相关的问题，可以分给多个 Agent 并行处理。
并行处理

作用：当多个问题彼此独立时，让不同 Agent 分工并行，不要一个一个顺着排队查。

适合什么时候用：多个测试文件失败、多个子系统同时出问题、互不相关的 bug 同时存在。

核心原则：独立问题独立查，能并行就并行。

给小白的理解：几个人同时查不同题目，比一个人挨个查更快。

subagent-driven-development 一个任务配一个新子 Agent，任务结束后再做两轮 review。
子 Agent 开发

作用：把计划里的每个任务交给独立子 Agent，先让它实现并自检，再做 spec review，再做 code quality review。

适合什么时候用：你已经有明确计划，而且任务彼此可以拆开。

核心原则：每个任务都要经历“实现 - 规格检查 - 质量检查”的闭环。

给小白的理解：像每道题都交给一个专门的人做，再让两个人帮你检查。

executing-plans 在独立会话里按计划逐步执行，并在检查点停下来确认。
执行计划

作用：拿着已经写好的计划，逐步推进，不在执行中临时乱改方向。

适合什么时候用：有明确方案、步骤很多、需要阶段性检查的时候。

核心原则：先读计划，再执行；中间遇到阻塞要停，不要猜。

给小白的理解：照着路线图走，走到检查点再确认下一步。

finishing-a-development-branch 工作做完后，先验证，再决定合并、发 PR、保留还是丢弃。
收尾

作用：把开发最后一步变成可控流程：先检查测试，再给出 4 个明确选项，再执行用户选择。

适合什么时候用：功能完成、准备提交、准备合并、准备清理工作区的时候。

核心原则：收尾不是“我说完了”，而是“验证通过后再选择去向”。

给小白的理解：做完作业后，还要再检查一遍，然后再交。

writing-skills 写新 Skill 或修改旧 Skill 时，用测试思维验证它真的能指导行为。
写技能

作用：当你要新增或修改 Skill 时，先设计压力场景，再看没有 Skill 时会怎样，最后补足规则，再复测。

适合什么时候用：创建 Skill、编辑 Skill、验证 Skill 是否真的有效。

核心原则：Skill 不是随便写几句说明，而是要能通过真实压力测试。

给小白的理解：不是写了说明就行，要看别人照着做时会不会真的成功。

推荐顺序：先用 brainstorming 定方向，再用 writing-plans 拆任务，执行时配合 using-git-worktrees、test-driven-development、systematic-debugging、verification-before-completion，最后用 review 和 finishing-a-development-branch 收尾。

6. 子 Agent 怎么用

子 Agent 可以理解成“把同一个大任务拆给几个专门的小助手同时处理”。主 Agent 负责统筹方向、整合结果和最终验证，子 Agent 负责独立查资料、读模块、写局部实现或做 review。

先记住一句话：子 Agent 不是越多越好。任务能独立拆开时才适合并行；如果几个子任务互相依赖很强，硬拆反而会制造冲突。

什么时候适合用

  • 多个问题彼此独立，比如分别排查前端、后端、测试失败。
  • 多个模块可以并行阅读，比如认证、订单、日志各有入口。
  • 需要多视角检查，比如一个 Agent 实现，一个 Agent 做 code review。
  • 资料搜集量较大，比如一个查官方文档，一个查项目代码。

什么时候不适合用

  • 任务很小，一个文件几行改动就能解决。
  • 需求还没说清楚，拆出去只会让多个 Agent 一起猜。
  • 所有步骤必须严格串行，比如先迁移数据库再改业务代码。
  • 同一段代码会被多个 Agent 同时修改，容易互相覆盖。
角色 主要负责什么 你要怎么约束它
主 Agent 理解需求、拆任务、分配子 Agent、合并结论、做最终验证。 要求它先给拆分方案，说明每个子任务的输入、输出和验收标准。
研究型子 Agent 查 EXA、Context7、官方文档、网络资料，给出可引用的依据。 要求它区分“来源结论”和“自己的推断”，不要把不确定内容写成事实。
代码理解子 Agent 用 CodeGraph 或代码搜索理解某个模块、调用链、影响范围。 要求它只输出代码地图和风险点，先不要直接改代码。
实现型子 Agent 按明确计划完成局部实现或局部测试。 限制它只改指定范围，并要求给出改了哪些文件、怎么验证。
Review 子 Agent 从正确性、可维护性、测试缺口、安全风险角度检查结果。 要求它优先列问题和证据，不要只说“看起来没问题”。

拆任务的标准

每个子任务都应该有清晰边界：看哪个目录、查哪类资料、输出什么结论、不能碰什么文件。

合并结果的标准

不要直接相信子 Agent 的结论。主 Agent 要把它们的输出重新对齐需求，检查是否互相冲突。

最终验证的标准

无论用了几个子 Agent，最后都必须回到测试、构建、预览、截图、人工验收这些真实证据上。

请先判断这个任务是否适合使用子 Agent。
如果适合，请按下面格式拆分：

1. 主 Agent 负责什么
2. 需要几个子 Agent
3. 每个子 Agent 的任务边界
4. 每个子 Agent 允许使用哪些工具
5. 每个子 Agent 禁止修改什么
6. 每个子 Agent 必须交付什么结果
7. 主 Agent 如何合并结果并最终验证

如果不适合使用子 Agent，请说明原因，并用单 Agent 流程完成。

7. CodeGraph 相关技能

CodeGraph 的思路和普通“搜索文件”不一样。它先把代码结构建立成一张图，再让 AI 按符号、调用关系、影响范围来查。 这对大项目特别有用，因为你真正关心的往往不是“这个词在哪”，而是“改它会影响谁”。

它最适合回答的问题

  • 这个函数是谁调用的？
  • 这个入口往下会走到哪里？
  • 我改这个符号会影响什么？
  • 项目里和这个功能相关的核心路径在哪？

它不适合替代的事情

  • 它不能代替真正的测试和构建。
  • 它不能代替业务确认。
  • 它也不是“写代码前就不用思考”。

CodeGraph 的典型用法

  • 先用 codegraph_context 拿整体上下文。
  • 再用 codegraph_trace 追踪调用链。
  • 需要源代码时，用 codegraph_explore 看相关文件。
  • 要判断影响面时，用 codegraph_impact。

给小白的一句话

如果你在大项目里迷路了，CodeGraph 就像一张“项目地图”。先看地图，再动刀，出错会少很多。

请先用 CodeGraph 帮我建立这段代码的地图：
1. 核心入口在哪里
2. 调用链怎么走
3. 哪些地方会被这次改动影响
4. 先不要改代码，只给我理解结果

8. 各家大模型怎么选

这一章是面向 AICoding 的实践选型，不是永久不变的官方排名。模型更新很快，所以更推荐把它当成“当前怎么用更顺手”的经验地图： 先看任务类型，再选模型，而不是只看谁在榜单上更高。

重要提醒：下面有些判断属于实践经验总结，尤其是“适合什么场景”。真正用于生产前，仍然要用你的项目样例、成本、速度和验证结果做一次小规模评估。
模型 / 系列 实战定位 最适合的 AICoding 场景 不建议怎么用
GPT-5.5 / GPT-5.4 全流程开发主力 从需求澄清、方案设计、代码实现、工具调用、调试、测试到总结交付，适合覆盖完整开发链路。 不要只靠模型硬写。仍然要搭配系统提示词、MCP、Skill 和验证流程。
Claude Opus / Sonnet 系列 中途接入项目、顺着已有代码写 适合读已有代码风格、模仿项目结构、在现有模式下继续补功能。尤其适合“这个项目已经有一套写法，照着写”。 不要在没有上下文时让它凭空设计整个系统。它更适合跟随已有代码和约束。
Claude Fable 5 最高质量档，价格高昂 适合高价值架构判断、复杂重构、关键代码 review、疑难问题分析，以及需要极强综合判断的任务。 不适合所有日常小任务都用。成本高，应该留给难题和关键节点。
Gemini 前端设计灵感和视觉探索 当你对前端样式、页面视觉、布局气质暂时没有灵感时，可以用它做设计方向、视觉草图、页面风格探索。 不要只让它输出“好看的页面”就直接上线。前端仍要检查响应式、可访问性、交互状态和代码质量。
DeepSeek 中文理解强，能力接近 GPT-5.4 中文需求、中文业务文档、中文上下文理解非常强，适合中文项目讨论、需求拆解、中文技术解释和中等复杂度开发。 遇到最新 API、框架版本、外部事实时仍要查证，不要把中文表达流畅当成事实准确。
GLM / MiMo / Kimi / MiniMax 下位替代和成本补位 适合预算敏感、轻量问答、普通文案、简单代码辅助、摘要、低风险批量任务。 不要优先拿来做最复杂的全流程开发、关键架构决策或高风险重构。

全流程开发

优先看 GPT-5.5 / GPT-5.4。它们适合从规划到执行再到验证的完整链路，尤其是工具调用多、上下文长、任务复杂时。

已有项目续写

优先看 Claude Opus / Sonnet 系列。已有代码风格、目录结构、测试习惯越明确，它们越适合“照着现有模式继续写”。

最高质量难题

可以把 Claude Fable 5 放在关键节点使用，例如架构评审、复杂 Bug 根因分析、重大重构前 review。

前端灵感

Gemini 适合在没有视觉方向时帮你打开思路，比如布局、色彩、组件氛围、页面节奏。

中文场景

DeepSeek 很适合中文表达、中文业务理解、中文需求拆解。中文语境越重，它的优势越明显。

成本补位

GLM、MiMo、Kimi、MiniMax 可以作为下位替代，用在低风险、轻量、可批量验证的任务上。

9. 一套推荐工作流

如果你想把这些东西串起来，最稳的顺序其实很简单：先定方向，再定计划，再隔离工作区，再查证据，再实现，再验证，再 review，再收尾。

1

先用 brainstorming 把需求说清楚

需求不清时先设计，不要直接开写。目标、边界、方案先定住。

2

再用 writing-plans 拆成小步骤

每个步骤都要有文件、代码、验证方法，别让执行时临时猜。

3

开 isolated worktree，避免互相污染

中型以上任务，最好让这次改动有自己的工作区和自己的提交节奏。

4

查证据：EXA / Context7 / CodeGraph

外部资料、官方文档、项目结构，分别用合适的工具补齐。

5

实现时配合 TDD 和系统化调试

先写失败测试，再写最小实现。出错时先找根因，不要乱补丁。

6

完成前做 verification-before-completion

不要凭感觉说完成。先拿验证结果，再给结论。

7

必要时请求 review，收到后认真接收

review 是为了减少漏网问题，不是礼貌性聊天。

8

最后用 finishing-a-development-branch 收尾

测试、合并、保留还是丢弃，都走明确选项，不含糊。

最关键的一点：“AI 不出幻觉”不是单靠一个更强模型就能解决的。它是提示词、Skill、MCP、验证和 review 一起把风险压下来的结果。

10. 常见误区

很多 AICoding 翻车，不是因为 AI 太笨，而是因为流程太松。下面这些坑最常见。

误区 1：把 Skill 当魔法按钮

Skill 不是按一下就“自动正确”。它是工作方法，需要配合清晰任务和正确工具。

误区 2：不给证据，却要求准确

不查资料、不看代码、不给上下文，还要求 AI 不出错，这是在逼它猜。

误区 3：一次改太多

改动越大，越难判断哪里出错。大改动最应该拆分成多步。

误区 4：没有验证就宣布完成

“我觉得好了”不是证据。测试、构建、回归检查才是证据。

误区 5：把模型说的每句话都当真

AI 可能会给出看起来很顺的答案，但顺不等于对。尤其是版本、接口、调用链，必须核验。

误区 6：不让查资料，却要写最新代码

这几乎是幻觉的温床。越是新框架、新版本、复杂项目，越需要查证。
